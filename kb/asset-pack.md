# The asset pack — `assets.pak`

**Status:** built and verified against the real ISO, 2026-08-01.
**Producer:** `tools/dcasset/dcasset.py pack` (+ `assets_scan.py`, `pack.py`).
**Consumer:** the future `dc/` runtime. This file is the contract between them.
**Verification:** `dcasset packverify` re-checks a built pack against the ISO
and the source tree; the harness should run it before every CDI build.

---

## 1. Why

`pc/src/pc_assets.c` (generated by `pc/tools/gen_runtime_assets.py`) loads the
whole decompressed `foresta.rel` (**15,640,056 B**) *and* the whole `main.dol`
(**918,720 B**) into RAM, `memcpy`s 16,365 assets out of them by absolute byte
offset, then `free()`s both:

```c
static u8* g_rel_data = NULL;                       /* pc_assets.c:16 */
static u8* g_dol_data = NULL;
void pc_load_asset(const char* bin_path, void* dest, unsigned int size,
                   unsigned int rom_off, int rom_src, int swap_type) {
    u8* rom = (rom_src == SRC_REL) ? g_rel_data : g_dol_data;
    if (rom) { memcpy(dest, rom + rom_off, size); loaded = 1; }
    ...
    if (loaded) do_swap(dest, size, swap_type);
}
```

**16,558,776 bytes** held simultaneously, on a machine with **16,777,216**.
Not a steady-state cost — it is a boot-time *peak*, freed at the end of
`pc_assets_init()` — but the peak is the thing a stock Dreamcast cannot pay,
and it sits on top of the ~8.2 MB of static destination arrays (see §7).

Only **8,787,262 B** of those two blobs is ever touched. The pack ships
exactly those bytes, pre-swapped, in the order the game reads them.

### Disc

`assets.pak` (8,917,568 B) **replaces** `foresta.rel` (15,640,056 B) on the
disc: 6,722,488 B smaller, and the DC no longer needs a Yaz0 decompressor or
a 15.6 MB scratch buffer at boot. Streaming the whole pack once at 500 KB/s
is **17.8 s** — that is the boot-time asset-load floor, and it is sequential.

## 3. On-disc format (v1)

All fields **little-endian**, all offsets **absolute byte offsets into the
file**, all integers `uint32_t`. Nothing needs conversion or relocation on
SH-4; the runtime can `fread` the header + index + sort table and use them
in place.

### 3.1 Header — 64 bytes at file offset 0

| off | size | field | value in the built pack | meaning |
|---|---:|---|---|---|
| `0x00` | 8 | `magic` | `"DCASSET1"` | ASCII, no NUL |
| `0x08` | 4 | `format_version` | 1 | bump on any layout change |
| `0x0C` | 4 | `header_size` | 64 | where the source table starts |
| `0x10` | 4 | `flags` | 1 | bit0: *every* chunk is pre-swapped |
| `0x14` | 4 | `source_count` | 2 | number of source-table entries |
| `0x18` | 4 | `index_offset` | 96 | first index entry |
| `0x1C` | 4 | `index_entries` | 3,188 | chunk count |
| `0x20` | 4 | `sorted_offset` | 38,352 | first sort-table entry |
| `0x24` | 4 | `payload_offset` | 51,104 | first payload byte |
| `0x28` | 4 | `payload_bytes` | 8,866,464 | payload length |
| `0x2C` | 4 | `chunk_align` | 32 | payload chunk alignment |
| `0x30` | 4 | `max_chunk_bytes` | 137,856 | largest chunk; buffer sizing |
| `0x34` | 4 | `payload_crc32` | `0xB0C3798D` | zlib CRC-32 of the payload |
| `0x38` | 4 | `rel_blob_size` | 15,640,056 | sanity: the REL this was built from |
| `0x3C` | 4 | `dol_blob_size` | 918,720 | sanity: the DOL this was built from |

A loader **must** check `magic` and `format_version`, and **should** check
`rel_blob_size` / `dol_blob_size` against the constants it was compiled with.
A stale pack built from a different master is otherwise silent corruption.

### 3.2 Source table — `source_count` × 16 bytes at `header_size`

| off | size | field | REL entry | DOL entry |
|---|---:|---|---|---|
| `+0` | 4 | `source_id` | 0 (`SRC_REL`) | 1 (`SRC_DOL`) |
| `+4` | 4 | `chunk_count` | 3,170 | 18 |
| `+8` | 4 | `blob_size` | 15,640,056 | 918,720 |
| `+12` | 4 | `max_referenced_end` | 14,403,360 (`0xDBC720`) | 825,920 (`0xC9A40`) |

Informational / assertable. Lookup does not need it — `source_id` is carried
in every index entry.

### 3.3 Chunk index — `index_entries` × 12 bytes at `index_offset`

Stored **in payload order** (= boot load order, see §4).

| off | size | field | meaning |
|---|---:|---|---|
| `+0` | 4 | `src_off` | byte offset of the chunk inside its source blob |
| `+4` | 4 | `pack_off` | absolute byte offset of the chunk in this file |
| `+8` | 4 | `len_flags` | packed, see below |

```
len_flags bits 0..27   chunk length in bytes  (max 137,856 here; cap 256 MB)
          bits 28..29  source_id (0 = foresta.rel, 1 = main.dol)
          bit    30    reserved, must be 0
          bit    31    PRESWAPPED: bytes are already byte-swapped;
                       the runtime MUST NOT call do_swap() on them
```

### 3.4 Sort table — `index_entries` × 4 bytes at `sorted_offset`

`uint32_t` chunk indices, sorted ascending by `(source_id, src_off, end)`.
This is the binary-searchable view; the index itself is in load order and is
*not* sorted. 12,752 B buys an O(log n) fallback that makes the loader
immune to any change in call order.

### 3.5 Payload — `payload_bytes` at `payload_offset`

Chunks in load order, each starting at a multiple of `chunk_align` (32).
Inter-chunk padding is zero-filled and is never addressed by any index entry.

## 4. Chunking and ordering — why load order, and why chunks overlap

The boot-time asset load is **statically known and fully deterministic**:

1. `pc_assets_init()` walks `s_assets[]` (14,495 entries) in table order;
2. then calls 769 `_pc_load_src_*()` functions in `pc_assets.c`'s textual
   order; each executes its own `pc_load_asset` calls in textual order.

`assets_scan.py` replays that exact sequence (all 769 functions were located
in `src/`, none missing, none uncalled). `pack.py` then groups **consecutive**
references that are also **contiguous in the blob** into one chunk: a
reference joins the open chunk if it has the same source and starts at or
before the chunk's current end.

That grouping produces 3,188 chunks whose payload order *is* the read order.
The cost is 64,640 bytes (0.73%) of blob content duplicated where a byte range
is read at two different times; disc space is free (§ the whole DC disc is
5.3% of a CD-R), seeks are not.

Measured, all three layouts, same 16,365 reads:

| `--order` | index entries | file | backward reads | min window |
|---|---:|---:|---:|---:|
| **`load` (default)** | **3,188** | **8.50 MB** | **82** | **7,520 B** |
| `first-touch` (merged spans, ordered by first use) | 2,509 | 8.43 MB | 3,302 | 8,527,952 B |
| `source` (merged spans, source-offset order) | 2,509 | 8.43 MB | 13,979 | 8,801,824 B |

The merged-span layouts save 70 KB of disc and cost 3,302 / 13,979 backward
seeks. At even 50 ms a seek that is 165 s / 700 s added to boot. The load
layout's 82 backward reads all fall within 7,520 bytes, i.e. inside any
sane read-ahead window — see §6.

## 5. Lookup algorithm the runtime implements

`pc_load_asset(path, dest, size, rom_off, rom_src, swap)` becomes:

```c
/* resident state */
static pak_entry_t *g_index;      /* index_entries * 12 B, load order   */
static uint32_t    *g_sorted;     /* index_entries * 4 B, (src,off) asc */
static uint32_t     g_cursor;     /* last hit; the whole point          */

static int fits(uint32_t i, int src, uint32_t off, uint32_t size) {
    pak_entry_t *e = &g_index[i];
    return  ((e->len_flags >> 28) & 3) == (uint32_t)src
        &&  e->src_off <= off
        &&  off + size <= e->src_off + (e->len_flags & 0x0FFFFFFFu);
}

static uint32_t pak_find(int src, uint32_t off, uint32_t size) {
    /* 1. cursor fast path: this hit 16,365 / 16,365 times in the
     *    measured boot, so the binary search below never ran at all. */
    if (fits(g_cursor, src, off, size))                 return g_cursor;
    if (g_cursor + 1 < g_count
        && fits(g_cursor + 1, src, off, size))          return ++g_cursor;

    /* 2. binary search the sort table on the key (src, src_off) */
    int lo = 0, hi = (int)g_count;                 /* greatest k with */
    while (lo < hi) {                              /* key[k] <= (src,off) */
        int mid = (lo + hi) >> 1;
        uint32_t i = g_sorted[mid];
        uint32_t s = (g_index[i].len_flags >> 28) & 3;
        if (s < (uint32_t)src || (s == (uint32_t)src
                                  && g_index[i].src_off <= off)) lo = mid + 1;
        else                                                     hi = mid;
    }
    /* 3. walk back over chunks that share the source and start at or
     *    before off. Chunks may overlap in source space (§4), so the
     *    first candidate is not always the right one. Measured maximum
     *    back-scan depth on this pack: 0. */
    for (int k = lo - 1; k >= 0; --k) {
        uint32_t i = g_sorted[k];
        if (((g_index[i].len_flags >> 28) & 3) != (uint32_t)src) break;
        if (fits(i, src, off, size)) { g_cursor = i; return i; }
    }
    return PAK_NOT_FOUND;                          /* fatal: stale pack */
}

void pc_load_asset(const char *path, void *dest, unsigned size,
                   unsigned rom_off, int rom_src, int swap) {
    if (rom_src == SRC_NONE) { /* .bin fallback, 1 call site */ return; }
    uint32_t i  = pak_find(rom_src, rom_off, size);
    pak_entry_t *e = &g_index[i];
    pak_read(dest, e->pack_off + (rom_off - e->src_off), size);
    if (!(e->len_flags & 0x80000000u)) do_swap(dest, size, swap);  /* never
                                        taken on this pack: all preswapped */
}
```

Cost per asset: two `fits()` compares and one read. No allocation, no search.

## 6. Read-ahead strategy

Model the pack as **one file handle that is never rewound**, plus a sliding
window holding the last `B` bytes read. A request inside the window is a
`memcpy`; a request past it streams forward (contiguous, no seek); a request
starting before `head - B` is a **window fault** — the only case that forces
a real backward seek.

Simulated over the actual 16,365-read boot sequence:

| window `B` | window faults | reads served from window | bytes streamed | boot @500 KB/s |
|---:|---:|---:|---:|---:|
| 2,048 | 33 | 48 | 8,917,568 | 17.8 s |
| 4,096 | 9 | 72 | 8,917,568 | 17.8 s |
| **8,192** | **0** | 81 | 8,917,568 | 17.8 s |
| 16,384 | 0 | 81 | 8,917,568 | 17.8 s |
| 65,536 | 0 | 81 | 8,917,568 | 17.8 s |

**8 KB is the correctness floor; 64 KB is recommended** — not for seeks (there
are none above 8 KB) but to amortise KOS `fs_read` / ISO9660 call overhead
across ~136 reads instead of ~1,090. Beyond 64 KB nothing improves.

Concretely, the loader should:

1. `fs_open("/cd/files/assets.pak", O_RDONLY)` once, at the top of
   `pc_assets_init`, and keep it open (later lazy paths call `pc_load_asset`
   too — do not close it).
2. Read header + source table + index + sort table (51,104 B) into a
   permanent allocation.
3. Maintain a 64 KB window `[head - len, head)`. For a request at `pos`:
   * inside the window → `memcpy`;
   * `size >= B` → read straight into `dest` from `head` forward;
   * otherwise → refill forward from `head` and `memcpy`.
4. Never seek backwards. If a window fault ever happens, it means the call
   order diverged from the pack's build-time assumption; log it (it is also
   exactly the case the `pak_find` binary-search fallback exists for) and
   `fs_seek` — correct, just slow.
5. Optionally CRC-check the payload once in a debug build against
   `payload_crc32`; do not do it in release, it costs a second full read.

Because the read is strictly forward, `mkdcdisc` should place `assets.pak`
contiguously and, ideally, early — it is read once, in full, at boot.

## 7. Honest caveats — read before trusting the number

**a) The 8.66 MB figure held; it did not grow.** The original caveat was that
only `pc_load_asset` sites were parsed. Audited this pass:

* `g_rel_data` / `g_dol_data` are `static` in `pc_assets.c` and referenced
  **only** inside `pc_load_asset` (grep over `src/`, `pc/`, `include/`).
* `pc_disc_extract_rel()` / `pc_disc_extract_dol()` have exactly one caller
  each — `pc_assets_init()`.
* `boot.c:757` compiles `LoadLink("/foresta.rel.szs")` out under `TARGET_PC`
  ("skipping REL module load (code is statically linked)"), so the REL is
  never loaded as a code module either.
* Reconciliation is exact: 2,641 textual `pc_load_asset` occurrences under
  `src/` = 770 prototypes + 1,871 parsed calls + **0 unaccounted**, plus the
  14,495-entry table. `dcasset pack` **refuses to build** if that ever
  becomes non-zero.
* One call site is outside any generated loader function —
  `src/furniture/ac_radio_test.c:32`, `rom_src = SRC_NONE` — so it uses the
  `.bin` fallback and contributes no blob bytes. It is reported by name.

Conclusion: for `foresta.rel` and `main.dol`, 8,787,262 distinct bytes is the
**complete** footprint, not a lower bound.

**b) The saving is the *source* blob, not the assets.** The destinations are
statically allocated arrays compiled into the binary
(`Vtx act_ant_v[0xB0 / sizeof(Vtx)];` and 15,725 others). Their extents sum
to **~8,617,214 B (8.22 MB)** and they stay resident whether the bytes arrive
from a blob or from the pack. The pack removes 15.68 MB of *peak*; it does
not remove the 8.22 MB of BSS/data. **That 8.22 MB is the next RAM problem
and it is larger than everything else in the ledger** — `kb/mem-budget-m1-sh4.md`
must carry it as a separate line, and the eventual fix is a different one
(demand-load per asset into pooled storage, which this pack format already
supports since every asset is individually addressable).

**c) Pre-swapping is total, but verify it stays total.** All 3,188 chunks were
pre-swapped: no two references disagreed about any byte. If a future
regeneration of `pc_assets.c` creates a conflict, the affected chunk is
emitted raw with `PRESWAPPED` clear and the runtime swaps it — correct, just
slower. The tool prints the count and the conflicting call sites. Do not
delete the `do_swap` path from `pc_load_asset`.

**d) There are four *other* byte-swap passes the pack does not cover.**
`boot.c` calls `pc_bswap_raw_display_lists()`, `mFM_InitActableEndian()`,
`pc_bswap_u8_tlut_palettes()` and `pc_bswap_house_pos_list()` after the asset
load. Those operate on the destination arrays, not on the blob, so they are
out of scope here — but they are the same kind of boot-time SH-4 tax and
should be measured next.

**e) `foresta.map` / `static.map` are not read by the game.** See §8; they can
be dropped from the disc.

## 8. Verdict on `foresta.map` / `static.map` (5,402,023 B, 20.4% of content)

**They are exception-handler symbolication only. Drop them.** Evidence:

* The only thing that ever names a `.map` file is
  `src/static/boot.c:695`, `JC_JUTException_setMapFile("/static.map")` →
  `JUTException::appendMapFile()`, which only pushes the *string* onto
  `sMapFileList`. Nothing is read there.
* The only code that opens one is
  `JUTException::queryMapAddress_single()` (`JUTException.cpp:694`), via
  `JUTDirectFile::fopen()` → `DVDOpen()`.
* Its only callers are `queryMapAddress()` ← `showMapInfo_subroutine()` ←
  `showStack()` / `showGPRMap()` ← `printDebugInfo()` ← `errorHandler()`,
  which is installed by `JUTException::create()` for `OS_ERROR_DSI`, `ISI`,
  `PROGRAM`, `ALIGNMENT`, `PROTECTION` (`JUTException.cpp:93-97`). It runs
  only after a PowerPC CPU exception.
* `foresta.map` is reached the same way: `queryMapAddress()` does
  `strcpy(buffer, mapPath); strcat(buffer, ".map")` where `mapPath` is the
  module name recovered from the loaded REL — `"/foresta"` → `"/foresta.map"`.
  On the DC the REL is never loaded as a module at all (§7a), so that path
  cannot even be reached.
* Stronger still, `showMapInfo_subroutine()` opens with
  `if ((address < 0x80000000) || (0x82ffffff < address)) return false;` —
  a hard-coded GameCube MEM1 window. Dreamcast P1/P2 addresses are
  `0x8C000000`+, above `0x82FFFFFF`, so on SH-4 the function returns false
  before touching a map file **even if the crash handler is ported**.
* No other reference exists: grep for `\.map` / `MapFile` / `queryMapAddress`
  across `src/` and `include/` returns only the sites above (the one other hit
  is a comment in `jsyswrapper.cpp`).

Dropping both saves **5,402,023 B** of disc and costs nothing on a platform
where the code that would read them is unreachable. `dvderr.c` was checked
specifically — it contains no map reference of any kind.

## 9. Reproducing

```bash
cd tools/dcasset
make pack          # -> $OUT/files/assets.pak + assets.pak.json
make packverify    # independent re-verification against the ISO
make lint
```

Runtime on the M4 host: ~1.3 s scan + Yaz0 extract, 0.03 s build, 0.13 s
verify; ~3 s wall including the two comparison layouts.

The build is verified three ways, every run:

1. **Swap self-test** — 45 cases comparing `pack.py`'s `array.byteswap()`
   fast paths against literal ports of the three C loops in `pc_assets.c`,
   at every size class including non-multiples of the element size (the C
   loops truncate; so do these).
2. **Full reference replay** — all **16,365** references are looked up
   through the §5 algorithm and the resulting destination bytes compared to
   `apply_swap(blob[off:off+size], swap)`, i.e. exactly what the PC loader
   would have produced. **8,884,894 bytes compared, 0 mismatches.**
3. **Payload CRC-32** re-computed from the written file.

`packverify` re-runs 1–3 against a pack read back off disk, so a truncated or
stale `assets.pak` fails loudly rather than as a mystery crash on boot.
